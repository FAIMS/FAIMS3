# ADR 0002: Unify the aws-cdk deployment config with `@faims3/build-config`

- Status: Accepted
- Deciders: Steve Cassidy
- Supersedes: n/a (complements ADR-0001)
- Date: (set on merge)

## Context

ADR-0001 established `@faims3/build-config` as the single source of truth for the
shared config chain (JSON → typed config → generated env → typed config) and the
mobile/`app`+`web`+`api` consumers have been migrated to parse their env through
it.

The `infrastructure/aws-cdk` deployment (`@faims3/infra-aws-cdk`) is the one
consumer still on a parallel track:

- It has its **own** JSON config, validated by `lib/config.ts` (`ConfigSchema`,
  ~815 lines), loaded from a **private config repo** via `config.sh`.
- It generates the deployed services' env with **hardcoded maps** inside the
  CDK components — `lib/components/conductor.ts` (API env: `PROFILE_NAME`,
  `EMAIL_*`, `RATE_LIMITER_*`, `AUTH_*`, …) and `lib/components/front-end.ts`
  (the `VITE_*` env for the web/app/docs builds). These hand-maintained maps are
  the same job build-config's `env-contract` already does, duplicated.
- Its config mixes **shared** deployment config (theme, notebook name, maps,
  autosuggest, security, SMTP, auth providers, support links, migration flags)
  with **AWS-specific** config (stack name, hosted zone, certificates,
  account/region, Route53 domains, EBS/CouchDB sizing, Fargate CPU/memory +
  autoscaling, backup vault, TTL cleanup, docker image, Secrets Manager ARNs).
- Secrets: the mobile CI build uses a SOPS-encrypted
  `secrets.enc.json`; the CDK references AWS Secrets Manager ARNs.

The goal is to make the CDK deployment config a **superset of the core
build-config config**: the shared part is validated and env-generated by
`@faims3/build-config`, and the CDK adds only the AWS-specific extension.

## Decision

### 1. Nested `{ core, aws }` CDK config

The CDK's top-level config becomes:

```jsonc
{
  "core": {
    /* validated verbatim by @faims3/build-config BuildConfigSchema */
  },
  "aws": {
    /* AWS-specific extension, validated by a CDK-local schema */
  },
}
```

- `core` is validated by `@faims3/build-config`'s `BuildConfigSchema` — the
  **same** schema the `app`/`web`/`api` use, so the shared config is
  guaranteed identical across all consumers.
- `aws` is a CDK-local `z.object({ … }).strict()` with the AWS-specific fields
  (stackName, hostedZone, certificates, aws account/region, domains, couch/EBS,
  conductor Fargate/docker/autoscaling, backup, ttlCleanup, docs, and the AWS
  Secrets Manager ARN manifest — see §6).
- The CDK schema is `z.object({ core: <BuildConfigCore>, aws: <AwsSchema> })`.
  A flat literal superset was considered and rejected: it would force the CDK to
  re-declare/re-pick every core field and drift from the shared schema.

This requires `@faims3/build-config` to export its **core** object schema (the
`z.object({…})` before the invariants transform) so the CDK can compose it. The
existing `BuildConfigSchema` (= core + invariants transform) is unchanged.

### 2. Domains: base + per-service names, with a local override

The core models the deployment's domain structure and **derives** the concrete
endpoints, instead of storing concrete URLs:

```jsonc
"domains": {
  "base": "faims.example.com",
  "protocol": "https",
  "services": {
    "conductor": "api",
    "couch": "couchdb",
    "web": "dashboard",   // varies per deployment (another deployment: "web")
    "app": "app",
    "docs": "docs"
  },
  "localOverride": {      // optional; when present these hosts are used verbatim
    "conductor": "localhost:8080",
    "couch": "localhost:5984",
    "web": "localhost:3001",
    "app": "localhost:3000"
  }
}
```

Derivation (implemented in `@faims3/build-config` so `app` build, `web` build
and the CDK all share it):

- production: `conductorUrl = https://api.faims.example.com`,
  `webUrl = https://dashboard.faims.example.com`, …
- local: if `localOverride[service]` is present, the host is that literal and
  the protocol defaults to `http`.

This replaces the current concrete-URL `endpoints` group with a derived one.
Consequence: the `app`-build conductor URL and the CDK's deployed conductor URL
are derived from the same `core.domains`, so they cannot drift. The CDK's
`aws.domains` (Route53 subdomain prefixes) set up DNS/CDN to _match_ the derived
URLs.

Landed **backward-compatible**: `domains` is an _optional_ group, so existing
configs that still store concrete `endpoints` keep working unchanged. When
`domains` is present it overrides the derived endpoint fields (`apiUrl`,
`webUrl`, `appUrl`, `couchdbPublicUrl`, `conductorUrls`); the non-domain
endpoint fields (`couchdbInternalUrl`, the app public URLs, `redirectWhitelist`)
keep their own defaults/input. The committed configs' migration from concrete
`endpoints` to `domains` (and the eventual removal of the concrete group) lands
with the config migration below.

A production env omits `localOverride`; a local/dev env sets it. (An explicit
`environment` switch was considered and rejected — the `localOverride` presence
is the switch, and it avoids a second axis of "mode".)

### 3. The CDK depends on `@faims3/build-config`

The CDK takes a normal workspace dependency on `@faims3/build-config` and reuses
its core schema and env-contract directly (not a copy). `aws-cdk synth`/deploy
resolves the **built** module (`build/src/index.js`); turbo `^build` builds it
first. Note the CDK currently pins its own `zod` (4.4.x) while build-config uses
4.1.x — see §7 (align to one version).

### 4. Theme: drop `bubble`

The CDK's `uiTheme` enum (`bubble | default | bssTheme | fieldmark`) adopts the
shared core theme enum (`default | fieldmark | bssTheme`). `bubble` is retired.

### 5. Env generation via the shared env-contract

The CDK stops hand-generating env. Instead:

1. Load `{ core, aws }`.
2. Overlay the AWS-resolved concrete endpoints (from `core.domains`, §2) and
   build `core.endpoints.redirectWhitelist` (conductor + app + web URLs, the
   `appId://` scheme, and the localhost entries when `aws.conductor.localhostWhitelist`).
3. Call build-config's `buildEnvMapFromRuntime(core, 'api')` and
   `buildEnvMapFromRuntime(core, 'apps')` to produce the API env and the
   `VITE_*` env.
4. Merge the small AWS-only env bits that are genuinely AWS-specific and belong
   in the CDK: `PROFILE_NAME`, `KEY_SOURCE=AWS_SM` + `AWS_SECRET_KEY_ARN`,
   docker image/tag, Fargate sizing, and the secret-slot → SM-ARN resolution (§6).

The CDK keeps a thin AWS-specific overlay; everything that is _shared_ config →
env comes from the shared env-contract, so the deployed env is guaranteed to
parse through the same `parseGeneratedEnv` the apps use.

### 6. Secrets: an optional `secrets` section, sourced per platform

Secrets are **optional, typed properties in a dedicated `core.secrets`
section** (option 2 — a separate section rather than co-located with each
config group). The committed `core.json` declares the **slots only** (empty);
real values never live in the committed core.

```jsonc
"secrets": {
  "auth":      { "cookieSecret": "", "authProviders": { "google": { "clientSecret": "" } } },
  "email":     { "smtpUser": "", "smtpPassword": "" },
  "observability": { "bugsnagApiKey": "" },
  "couchdb":   { "couchdbPassword": "" },
  "maps":      { "mapSourceKey": "", "autosuggestMapboxKey": "", "autosuggestMapTilerKey": "" },
  "mobile":    { "android": { "…keystore/match slots…": "" }, "ios": { "…match/Apple key slots…": "" } }
}
```

The secret **source** differs per platform; the same `core.json` is used by all:

- **SOPS platforms (mobile CI, Terraform, local dev):** a SOPS-encrypted
  `secrets.enc.json` (same repo) holds the values; decrypt + merge
  (`jq -s '.[0] * .[1]'`). This is the existing mobile-build pattern and also
  serves the **Terraform** deployment (age key held by Terraform, decrypt at
  plan/apply, inject as values — no Secrets Manager).
- **AWS:** the same slots are resolved from **AWS Secrets Manager**, which is
  the source of truth and **overrides** any value in the core. The `aws`
  section carries the slot → SM-ARN manifest (e.g.
  `aws.secrets = { authGoogleClientSecret: "arn:aws:secretsmanager:…", … }`).
  For AWS, `secrets.enc.json` is not used; SM wins.

**Invariant (enforced in the config validator / CI lint):** the committed
`core.json` must have **no non-empty value in any declared secret slot**. This
prevents a locally-convenient real secret from leaking into the AWS path (where
SM is the source of truth). The validator knows which fields are "secret slots"
from the schema's `core.secrets` shape.

Rationale: a mobile _client_ does not need server-side secrets (e.g. auth
`clientSecret`), so those were only in the mobile SOPS file for local-dev
convenience; keeping them as optional core slots (SOPS-filled) keeps local dev
easy while AWS resolves them from SM.

### 7. Align the zod version

The CDK pins `zod ^4.4.x`; build-config uses `^4.1.x`. Composing build-config's
schemas inside the CDK mixes two zod instances. Add a pnpm `overrides` entry (or
align the CDK's dependency) so both resolve to one zod version, avoiding
schema-identity surprises.

## Consequences / migration

- **build-config** gains: an exported **core** object schema (for CDK
  composition), the `core.domains` model + endpoint derivation, a `core.secrets`
  section (optional typed slots), and an "export env-contract is composable"
  surface for the CDK overlay.
- **CDK** `lib/config.ts` is restructured to `{ core, aws }`: the shared fields
  move out of `uiConfiguration`/`supportLinks`/`offlineMaps`/`addressAutosuggest`/
  `security`/`smtp`/`authProviders`/`bugMonitoring`/`conductor` into `core`
  (renamed/re-nested to build-config's groups); `aws` keeps the AWS-specific
  fields + the secret ARN manifest. `faims-infra-stack.ts` and components read
  `config.core.*` / `config.aws.*`.
- The **hardcoded env maps** in `conductor.ts`/`front-end.ts` are replaced by
  `buildEnvMapFromRuntime(core, …)` + a thin AWS overlay.
- The **private config repo** becomes one repo for all consumers:
  `core.json` (shared, non-secret, secret slots empty) + `secrets.enc.json`
  (SOPS) + `aws.json` (AWS extension + ARN manifest) per environment; the
  mobile build reads `core.json` + `secrets.enc.json`, the CDK reads
  `core.json` + `aws.json` (+ SM).
- **Existing CDK configs** in the private repo are migrated env-by-env to the
  new shape, gated by the validator (including the "no secret values in core"
  invariant).
- **Terraform** deployment adopts the same `core.json` + SOPS `secrets.enc.json`
  (no SM), decrypting at plan/apply.

## Open / follow-up

- Finalize the exact `core.secrets` slot list during the config migration
  (the structure in §6 is the shape; the precise per-provider/per-platform
  slots are filled in as the configs migrate).
- Confirm the CDK's nested `src/` (conductor docker image build) does not
  accidentally pull in the shared core config/secrets.
- The `core.domains` service-name set (conductor/couch/web/app/docs) should be
  confirmed against every real deployment's naming before the domain model is
  frozen.
